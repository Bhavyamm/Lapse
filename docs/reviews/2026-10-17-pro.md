# Review, Pro unlock screen (commit 1d5cd62), 2026-10-17

**Reviewed by**: Sonnet 5.5 (author model: Opus 5.5)
**Scope**: 7 files, `git show HEAD` (`src/app/pro.tsx`, `src/features/pro/purchase.ts`, `MailIcon`/`PeopleIcon`, Profile entry points now `router.push('/pro')`, `pro` registered as a modal, `pro.test.tsx`, `profile.test.tsx`)
**Verdict**: Changes requested

## Summary
The screen follows the intent: colours, fonts and radii come from `src/theme`, buttons use `role`/`aria-label`, the SVG gradient ids are made unique with `useId` (colons stripped, so they are valid in `url(#...)` on web), the yearly total uses `buildOverview` so running trials are excluded, a `busy` ref stops a second purchase while one is running, and the stubbed `purchasePro`/`restorePro` are intentional and not reported. `tsc`, lint and all 232 tests pass. The real problems are layout and navigation: the Unlock button sits at the end of the scroll content, so on a short phone or at large text it is below the fold, and Close, the Profile entry points and the post-purchase `leave()` can navigate twice. The tests miss both. I read the code and did not run it on a device; heights below are computed from the styles.

## Critical
None.

## Major
### 🟠 The Unlock Pro button is below the fold on short phones and large text, `src/app/pro.tsx:67-125`, `:228`
**Problem**: The button and "Restore purchase" live inside the `ScrollView` (`bottom` uses `marginTop: 'auto'`, which only pins them when the content is shorter than the screen). At default text size the content is about: top inset + 8, tag row 44, title 2 lines x 56 = 112 (3 lines = 168 on a 360 pt phone, where "Keep it forever." at 52 pt wraps), lede 3-4 lines x 23 = 69-92, two tiles x 128 + 10 = 266, button 64, restore 44, plus five 20 pt gaps and 14 and 24 pt of padding. That is roughly 790-850 pt before the top inset, more than an iPhone SE (667 pt) or a 640 dp Android phone shows, and a modal card on iOS is shorter still. The scroll indicator is hidden (`showsVerticalScrollIndicator={false}`), so nothing hints that the one button that matters is off screen. At larger text sizes (tiles grow past `minHeight: 128`, the lede wraps more) this happens on most phones.
**Why it matters**: The screen exists to sell one thing; on small phones the buyer sees the features and no button until they happen to scroll.
**Suggested fix**: Pin `bottom` outside the `ScrollView` (a footer `View` with `paddingBottom: insets.bottom + 16`, charcoal background) so only the title, lede and tiles scroll. Add a test at `fontScale` 2 / a short window that the Unlock button is not inside the scrollable content, or at least that it renders as a sibling of the `ScrollView`.

## Minor
### 🟡 Close, the Profile entry points and `leave()` can navigate twice, `src/app/pro.tsx:25`, `:79`, `src/app/(tabs)/profile.tsx:98`
**Problem**: (1) `leave` is not guarded: a double tap on Close calls `router.back()` twice while the modal is still animating, so the second call pops whatever is under it (or, if `canGoBack()` is false by then, `router.replace('/')` jumps the person from Profile to Home). The same happens if Close is tapped while a purchase is in flight and the purchase then resolves `'unlocked'`, since `explain` calls `leave()` again. (2) `openPro` uses `router.push('/pro')`, which does not de-duplicate: a double tap on "Unlock Pro" in Profile stacks two Pro modals, and closing one reveals the other.
**Why it matters**: Easy to hit on the one screen people tap quickly; the symptoms (landing on Home, or Pro "reopening") look like a bug in the app.
**Suggested fix**: Guard `leave` with a ref (`closing.current`), and have `explain` skip `leave()` when already closing. Use `router.navigate('/pro')` in Profile, or ignore a second press while the first is navigating. Add tests: pressing Close twice calls `router.back` once; unlocking after Close does not call it again.

### 🟡 The status bar stays light while the modal slides away, `src/app/pro.tsx:65`
**Problem**: `<StatusBar style="light" />` only reverts to the root `style="dark"` when the screen unmounts, which happens after the dismiss animation finishes. For the length of the animation (and during an interactive swipe-down on iOS) white status icons sit over the light Profile canvas and are unreadable. It does return to dark afterwards, so this is a flash, not a stuck state.
**Why it matters**: Cosmetic, but visible every time the modal is closed.
**Suggested fix**: Accept it, or set the light style from `useFocusEffect` and restore `dark` in the cleanup so it flips as soon as the screen blurs. Check on a device in Expo Go.

### 🟡 Yearly total is rounded, and can read "$0 a year", `src/app/pro.tsx:60`
**Problem**: `Math.round(yearly / 100) * 100` plus `formatMoney(...).slice(0, -3)` rounds to the nearest dollar, while Home and Profile show exact cents, so the same total reads "$305.88" elsewhere and "$306" here. A tracked total under 50 cents a year (a 1 cent monthly entry is allowed: `parsePrice` accepts any `cents > 0`) is truthy but rounds to `$0`, giving "You’re tracking $0 a year." The `slice(0, -3)` also silently depends on `formatMoney` always ending in `.dd`.
**Why it matters**: The headline number of the pitch should match the number the person has seen; the $0 case reads as broken.
**Suggested fix**: Show the exact `formatMoney(yearly)` (or format whole dollars with `Math.floor(yearly / 100).toLocaleString('en-US')` in a small helper in `billing.ts`), and omit the sentence when the rounded value is 0. Test a total that does not round-trip (e.g. 30,588 cents) and a 1 cent entry.

### 🟡 Test gaps, `src/__tests__/pro.test.tsx`
**Problem**: Not covered: the Close button (`router.back` / the `replace('/')` fallback when `canGoBack()` is false), "Restore purchase" resolving `'unavailable'` (the "Nothing to restore yet" copy), a second tap while a purchase is pending (the `busy` guard is the only double-tap protection and is untested), the yearly total excluding running trials, and a total that needs rounding. The `expo-router` mock has no `push`, so the Profile-to-Pro path is only checked from the Profile side.
**Why it matters**: The guard and the fallback are the behaviour most likely to regress when RevenueCat replaces the stubs.
**Suggested fix**: Add those cases; for the guard, make `purchasePro` return a pending promise, press twice, resolve, and assert it was called once.

## Nits
- `src/app/pro.tsx:104`: the button's `aria-label` ("Unlock Pro, $14.99. One-time...") does not contain the visible text "Unlock Pro · $14.99", so voice control saying the visible words may not match (WCAG 2.5.3). Use `Unlock Pro · $14.99. One-time. No renewal, ever.`
- `src/app/pro.tsx:48-55`: while a purchase is pending the button gives no feedback (no `aria-busy`, no dimming) and further taps are silently ignored; add `aria-busy`/`aria-disabled` once the real purchase is wired.
- `src/app/pro.tsx:84-92`: `role="heading"` on a Text with a nested Text and a `\n` is fine on iOS/Android; on web it renders as nested spans in the heading, so confirm the export reads "Pay once. Keep it forever." without a stray gap.

## Resolution

Fixed:
- Major, button below the fold: Unlock Pro and Restore purchase are a footer outside the scroll view, so they stay on screen on a 667 pt phone (checked in the web build) and the features scroll above them.
- Closing runs once, so a double tap on Close or a purchase finishing as it closes can't pop the screen underneath. Profile opens Pro with `navigate`, so a double tap can't stack two.
- The yearly total keeps cents when it's under a dollar and drops only a trailing ".00".
- The button's label starts with its visible text, "Unlock Pro · $14.99".
- Tests for Close, the totals and the label: 234 passing.

Deferred:
- Status bar colour during the closing animation, and a spinner while the store answers: with RevenueCat in the development build, when purchases are real.
