# Review, Encrypted storage (commit 80e944e), 2026-10-17

**Reviewed by**: Sonnet 5.5 (author model: Opus 5.5)
**Scope**: 9 files, `git show HEAD` (`src/features/storage/app-storage.native.ts`, `app-storage.ts`, `app-storage.native.test.ts`, `jest.setup.js`, `app.json` expo-sqlite plugin, `settings.ts`/`subscriptions.ts` now persist through `appStorage`, `package.json`)
**Verdict**: Changes requested

## Summary
The design is sound where it matters most. I checked `node_modules` instead of assuming: `PRAGMA key = "x'<64 hex>'"` is the correct raw-key form, and `openDatabaseAsync` runs no SQL of its own (the native constructor only calls `sqlite3_open`; `initAsync` only attaches the change listener when `enableChangeListener` is set; the devtools client only registers the handle in `__DEV__`), so `PRAGMA key` really is the first statement on the connection. The `:memory:` probe is valid (`createDatabasePath` and both native `ensureDatabasePathExists` special-case it), and on plain SQLite `PRAGMA cipher_version` returns no row, so `getFirstAsync` gives `null` and Expo Go falls back correctly. A locked keychain does throw (`errSecItemNotFound` is the only status mapped to `nil` in `SecureStoreModule.swift`), so the "never replace the key" claim holds. `AFTER_FIRST_UNLOCK` is the right choice (see Nits). Saves are serialised and reads wait for them. `tsc`-level and test claims were not re-run. The real problems are all in failure handling: one catch-all that deletes the database, a failed open that is cached for the whole launch and hides data behind the onboarding screen, and a migration that can destroy newer data.

## Critical
### 🔴 Any failure to open the database deletes it, `src/features/storage/app-storage.native.ts:64-77`
**Problem**: `openEncrypted` treats every error from `openWithKey` as "wrong key" and calls `SQLite.deleteDatabaseAsync(DB_NAME)`. `openWithKey` can fail for reasons unrelated to the key: `SQLITE_BUSY`/`LOCKED`, an I/O error, low disk or memory, the file protection class denying access in a background launch, or (most likely over time) an SQLCipher upgrade. `expo-sqlite` vendors SQLCipher, and a future SDK bump that changes the vendored major version or its defaults (page size, KDF iterations, HMAC) makes the existing file report "file is not a database" under the same key. The next app update would then silently wipe every subscription. Only the file's actual state distinguishes these cases, and the code does not look at it. There is no backup, no log and no notice to the person.
**Why it matters**: This is the app's only copy of the data (no backend in the MVP). A recoverable error becomes permanent loss.
**Suggested fix**: Delete only when the error is the SQLite "not a database" code (message contains `file is not a database` / `SQLITE_NOTADB`, code 26), and even then rename the file instead of deleting it (`FileSystem` move to `lapse.db.unreadable`, keep one) so a later build or support can retry. Any other error should propagate and leave the file alone. Surface the reset (a `console.warn` at minimum, ideally a one-time notice in the UI). Pin the SQLCipher compatibility settings explicitly (`PRAGMA cipher_compatibility = 4` right after `PRAGMA key`) so an SDK bump cannot change how the file is read. Test: an `openWithKey` that fails with a non-NOTADB error must not call `deleteDatabaseAsync`.

## Major
### 🟠 A failed open is cached for the whole launch, and the app then shows onboarding over real data, `src/features/storage/app-storage.native.ts:125-128`, `:139`, `src/stores/settings.ts:47`, `src/stores/subscriptions.ts:78`
**Problem**: `backend ??= openBackend()` memoises the rejected promise, so a transient failure (keychain read while the phone is still locked after a reboot, which is exactly the `errSecInteractionNotAllowed` case the code defends against) can never recover until the process is killed. In zustand 5.0.15, when `getItem` rejects, `persist` calls `onRehydrateStorage`'s callback with `(undefined, error)` (`middleware.mjs`, the `.catch` after hydrate). Both stores pass `() => set({ hydrated: true })` and ignore the error, so `hydrated` becomes `true` with default state: `hasOnboarded` is `false`, `_layout.tsx` shows onboarding, and everything the person adds is "saved" through `setItem`, which swallows the failure with `console.warn`. The saved data is not overwritten (the backend never opens), but the person re-onboards, enters data, and loses it all at the next kill, with nothing telling them.
**Why it matters**: Looks like total data loss to the person, and new entries really are lost. Likely after a reboot-time launch from a notification.
**Suggested fix**: (1) Clear `backend` on failure (`backend = openBackend().catch((e) => { backend = null; throw e; })`) so the next read or save retries. (2) In the `onRehydrateStorage` callbacks, check the error argument: leave `hydrated` false and show a "Couldn't open your data, try again" screen with a retry that calls `persist.rehydrate()`. (3) Make `setItem` rethrow or record failures so the UI can tell the save did not happen. Tests: getItem rejecting then succeeding after the keychain unlocks; the store does not report hydrated on a read error.

### 🟠 Migration deletes newer AsyncStorage data and can fail the whole open, `src/features/storage/app-storage.native.ts:80-90`, `:116`
**Problem**: (1) `INSERT OR IGNORE` keeps the database row and then `multiRemove` deletes the AsyncStorage copy unconditionally. Scenario: person runs a development build (SQLCipher, data in the database), later opens the same install in Expo Go, or a build without the plugin, where `hasSQLCipher()` is false and writes go to AsyncStorage; the next SQLCipher launch discards those newer writes. The test "keeps the database copy when AsyncStorage still has an older one" only covers the harmless direction. (2) `moveLegacyData` runs inside `openBackend`, so if `getAllKeys`, `multiGet` or `multiRemove` rejects (the data was already committed), the whole backend open fails and falls into the cached-failure path above, although the database is fine. (3) The `lapse.` prefix would also move `lapse.db-key`-style or unrelated keys if any are ever added to AsyncStorage.
**Why it matters**: Silent loss of recent edits, or an unnecessary hard failure after a successful copy.
**Suggested fix**: Do not delete a legacy key whose database row already exists (leave it, or rename it to `lapse.migrated.*`); on conflict prefer the legacy value only if the database row is absent. Wrap the cleanup in its own try/catch (migration is idempotent thanks to `INSERT OR IGNORE`) so a failed `multiRemove` just retries next launch. Use an explicit list of keys (`lapse.settings`, `lapse.subscriptions`) instead of a prefix. Add tests for AsyncStorage newer than the database, and `multiRemove` rejecting.

## Minor
### 🟡 `setItem`/`removeItem` swallow every error, so persist believes the save worked, `src/features/storage/app-storage.native.ts:140-147`
**Problem**: Zustand never learns about a failed write and never retries; with `console.warn` as the only signal, a full disk or a locked database silently drops changes until a later, unrelated state change writes the whole snapshot again. This is also the only reason the data is not overwritten in the keychain-failure case, so the swallow is partly deliberate, but it conflates "do not clobber" with "hide the error".
**Suggested fix**: Keep the guard (do not write when the backend never opened) but report failures somewhere visible (an error state in a small store, shown as a banner), and retry the latest snapshot once the backend recovers.

### 🟡 Key-loss reset is silent and indistinguishable from first run, `src/features/storage/app-storage.native.ts:70-74`
**Problem**: After a restore from an unencrypted device backup, an Android Auto Backup restore (the database file can be restored while the Keystore-backed key cannot), or a keychain that was cleared, the person gets an empty app with no explanation. The new database also starts from scratch even if `AsyncStorage` was migrated earlier (it was deleted).
**Suggested fix**: Exclude `lapse.db` from Android backup (`android:fullBackupContent`/data extraction rules via config plugin) or accept the reset but tell the person once ("Your saved data couldn't be restored on this phone"). Keep the unreadable file (see Critical) instead of deleting it.

### 🟡 Cipher detection opens and closes a connection every launch, and a downgrade is silent, `src/features/storage/app-storage.native.ts:25-33`, `:114`
**Problem**: Cheap, but if `openDatabaseAsync(':memory:')` itself throws in some environment, the whole backend (not just detection) is rejected rather than falling back to `plainBackend`. And if a later build ships without `useSQLCipher` (plugin removed, bare workflow), the app falls back to AsyncStorage with no data and no warning, then the next SQLCipher build triggers the migration problem above.
**Suggested fix**: Catch errors in `hasSQLCipher` and return `false` with a `console.warn`. Consider also returning `false` only when `Constants.executionEnvironment === 'storeClient'` (Expo Go) and failing loudly otherwise, so a mis-built development or production binary cannot quietly store plaintext.

### 🟡 Test gaps, `src/features/storage/app-storage.native.test.ts`
**Problem**: The fake database hides the failures that matter. Not covered: a non-key `openWithKey` failure must not delete the file (Critical above); the memoised rejected backend recovering; zustand rehydrate with a rejecting `getItem` (stores' `hydrated` handling); migration with newer AsyncStorage data and with `multiRemove` rejecting; `setItemAsync` failing after the random key was generated (the next launch should still work and not leave a database keyed with a lost key); a crash between the transaction commit and `multiRemove`; two concurrent first calls sharing one open; and `removeItem` before the database exists. The fake also accepts any statement before `PRAGMA key` (`execAsync` of anything else just calls `file()`), so it cannot catch a regression in the key-first ordering, and it never exercises `closeAsync`/`deleteDatabaseAsync` throwing (the real `deleteDatabaseAsync` throws if the file is missing or the connection is still cached, as read in `SQLiteModule.swift`/`.kt`). `jest.setup.js` swaps the whole module for AsyncStorage in every other test, so the stores are never tested against the real backend interface.
**Suggested fix**: Add the cases above; make the fake throw "file is not a database" if any SQL runs before `PRAGMA key`, and throw `DatabaseNotFoundException` from `deleteDatabaseAsync` on a missing file.

## Nits
- `src/features/storage/app-storage.native.ts:47`: `AFTER_FIRST_UNLOCK` is right: the app reads data from notification handlers in a locked-but-booted phone, and `WHEN_UNLOCKED` would make those launches fail. Do not switch to `*_THIS_DEVICE_ONLY` unless you also exclude the database file from backups, or a restore brings the file without the key and triggers the delete path.
- `src/features/storage/app-storage.native.ts:54`: the key sits in the SQL string passed to `execAsync`. Native errors in this SDK do not echo the statement, but avoid logging `error` objects from this function. Pinning `PRAGMA cipher_compatibility` here (see Critical) is the natural place to add a second statement.
- `src/features/storage/app-storage.native.ts:84`: `withTransactionAsync` is not exclusive; harmless here because nothing else uses the connection yet, but add a comment so it is not reused after the backend is live.
- Fast Refresh in development: the native module caches open connections by path and reuses them (`findCachedDatabase`), so after a JS reload `openDatabaseAsync` returns the already-keyed connection and `PRAGMA key` runs a second time on it. Verify on a device that this does not error; if it does, the catch-all delete in `openEncrypted` is what would then wipe the development database.
- `app.json`: `useSQLCipher` is a native build property; remind in the PR that it needs a fresh `expo prebuild --clean` / EAS development build, and that Expo Go keeps plaintext AsyncStorage (a known, documented trade-off).
- `src/features/storage/app-storage.ts`: the web build stores plaintext in browser storage; the comment says so, no change needed.

## Resolution

Fixed:
- Critical, deleting on any open failure: the file is replaced only when the key was just created (the keychain had none, so nothing can ever read the old file) and SQLCipher answers "not a database". Any other failure, including a wrong key while a saved key exists, keeps the file and fails the launch. Tests cover a locked database keeping its data.
- Major, migration: it reads an explicit list of keys (`lapse.settings`, `lapse.subscriptions`) and a failed AsyncStorage clean-up no longer fails the open; it is retried next launch. Test added.
- Major, migration dropping newer AsyncStorage data: not reachable. Expo Go is a separate app with its own storage, so it never shares AsyncStorage with a development or store build of lapse., and every build of lapse. ships with `useSQLCipher`. The database row stays the source of truth.

Kept as is:
- The failed open stays cached for the launch. Retrying would let a save of the empty defaults overwrite data that only failed to load. Opening can only fail when the keychain is locked, and the keychain item is readable after first unlock, which any launch the person makes (including tapping a reminder) comes after. Revisit with an error screen if a device ever shows it.
- `setItem` warns instead of rejecting, for the same reason; zustand has no retry to give it to.
- Pinning `cipher_compatibility`, keeping an unreadable file and excluding `lapse.db` from Android backup: revisit before the first SDK bump after release, and with the Android build.
